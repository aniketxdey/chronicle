Chronicle documentation

Chronicle turns recordings of your screen and system events into agent harnesses: context files, workflows, and a knowledge graph, all tailored to how you actually work.

Quickstart

Explore the app on a sample workday, in a minute and without recording.

Build a harness

Combine context files, workflows, and a graph for a line of work.

Connect an agent

Give Claude, Cursor, ChatGPT, and others access over MCP.

There are three levels, from general to specific:

LevelWhat it isExample
HarnessEverything an agent needs for a whole line of workRecruiting
Context fileGeneral guidance for one kind of session, like an agent fileResearching job companies
WorkflowA short procedure for one specific job, like a skillCustomizing resume bullets to keep their formatting and length

Screens and GIFs on this page show a synthetic sample workday, with no real screen data. Time spent waiting on a model is cut from the GIFs.

Quickstart

Install Chronicle, load the sample workday, and open the app. Nothing is recorded.

uv tool install "chronicle-context[graph]"
chronicle demo
chronicle serve

Open http://127.0.0.1:3030. The app opens on your latest recording, which here is Sample workday.

To see what an agent would receive, run this in another terminal:

chronicle context "finish the Acme export"

Your first recording

First, check what this machine can capture:

chronicle doctor
platform: darwin
[ok] front window: Cursor
[ok] idle time: 0.23
[ok] clipboard: readable
[ok] screenshot: 451 KB
[ok] OCR: tesseract
[!!] accessibility: grant Accessibility to the app that runs Chronicle

On macOS, give whatever runs Chronicle Screen Recording and Accessibility under System Settings › Privacy & Security. That's your terminal for chronicle record and chronicle serve, or the host app (Claude Desktop, Cursor, and so on) when an agent starts the recording. Browser URLs need a one-time Automation prompt per browser.

Then, on Recordings, pick a duration, say what you're about to do, and press Start recording. The panel shows live storage, frames, system events, pages, apps, and graph nodes. Press Stop and build graph when you're done, or let the timer finish.

You can also record from the terminal, or let an agent do it with start_recording:

chronicle record 30m --label "file an expense report"
chronicle stop
chronicle sessions

Durations run from 10 seconds to 7 days, written like 90s, 15m, or 1h30m. Press Ctrl-C to stop early. chronicle record captures in that terminal. With --detach it only starts the session, so a running chronicle serve has to do the capturing.

The mini window, in the sidebar, keeps a record button and timer on top of your other windows in browsers that support Document Picture-in-Picture.

Recordings

A recording is the source of everything else. Every 5 seconds by default, Chronicle samples the front app and window, the browser URL (macOS), screen text from the Accessibility tree or OCR, and a screenshot. It also logs system events: app_switch, window_focus, url_change, clipboard, idle_start, idle_end, session_start, and session_stop.

Keystrokes are never recorded. Password managers and System Settings are skipped, and emails, API keys, JWTs, and card numbers are redacted before anything is written.

When a recording ends, its graph is built. If a model is set up, it then refines the graph and writes context files and workflows in the background.

Opening a recording shows five tabs:

TabWhat's there
Knowledge graphThe graph, a node inspector, habitual app switches, and a chat about this recording
Contexts and workflowsWhat was generated from this recording, and buttons to make more
TimelineActivity by app, frames with screenshots, system events, tasks, and URLs
MeetingsTranscripts, decisions, and action items, when a speech-to-text tool sends them to POST /add
SearchGraph nodes, screen text, transcripts, events, URLs, and context files

All history, at the bottom of the recordings list, is every recording together, with older ones counting less.

Knowledge graph

Each recording gets its own graph of the apps, windows, sites, pages, search queries, topics, files, tickets, PRs, code identifiers, people, projects, customers, meetings, and tasks it contains. Every node and edge records the time spent on it and the frames it came from, so an agent can cite its evidence.

Drag to rotate, pinch to zoom, and select a particle to see what you did there, with its system events and frames in lists beneath it. Low-level kinds like windows and identifiers stay hidden until you choose Show everything or filter by kind. Refine with model has a model name the real work, merge duplicates, and add typed relations.

Ask about a recording

The chat beneath the graph answers from that recording only and cites frames, which you can open. Without a model, it falls back to searching what was recorded.

From the terminal

chronicle graph show --session 1
chronicle graph find acme
chronicle graph node pr:882
chronicle graph tasks --session 1
chronicle graph tune --session 1
chronicle ask "Where did we land on the Acme export columns?"
chronicle search invoice_id

graph tune needs a model. Without one, ask searches instead of writing an answer.

Context files

A context file is general guidance for one kind of session, like an agent file. It says where things stand, how to work, and what to reference. It isn't a procedure, because those are workflows. Use one alone for a small session like backtesting or making a presentation, or combine several in a harness.

Generate them

They're written automatically when a recording ends, if a model is set up. For older recordings, open Contexts and workflows and press Generate with model. The model reads everything recorded and names up to four files for the sessions it finds, such as "Researching job companies". Without a model, you get a General file and up to two others that match the recording's keywords, built from the evidence rather than written.

To write one for specific work, press Generate on the Contexts page, or New context file on a recording, and fill in:

  • Name and Description of the work: what the session is and what an agent should know going in.
  • Recordings to look at: one or several, combined into one file.
  • Earlier contexts to look at: where a recording disagrees with one, the file goes with the recording.
  • Workflows to use: the file tells the agent when to use each one by name, and lists them, without copying their steps.

You need to choose at least one source. Without a model, or if the model fails, the file is built from the sources themselves, without writing.

What's in one

A model-written file has these sections, leaving out any the evidence doesn't support:

  • Where things stand: what you were doing and where you left off.
  • How to work here: instructions from what you did, like which tools to use and what to check first.
  • Sections for that kind of work: tickets and PRs for coding, or sources read for research.
  • Reference: exact files, URLs, identifiers, and people.
  • Open threads: what's unfinished.

Each file also has its own small graph of the entities it relies on, and lists the workflows made from it or its recording. Download .md includes both, so one file works as a single upload.

Workflows

A workflow is a short, action-oriented procedure for one specific job, like a skill. It has a trigger, inputs written as {placeholders}, three to seven steps, what to confirm first, and its own small graph. Steps that send, submit, publish, pay, merge, or delete are marked Confirm first.

Press Generate with model on the Workflows page, or Make a workflow on a recording or context file:

  • Name and What it's for ask for one specific workflow. Leave both blank and the model finds up to five in what you chose.
  • Recordings to scan and Context files to scan set what it reads, so one workflow can draw on several recordings.

Every workflow must cite frames from what you chose, and anything citing other frames is rejected. If the model can't find the work there, you're told rather than given something made up. Workflows need a model that supports tool calls.

Downloads use the same frontmatter as skills (name and description), so a file can go straight into a skills folder.

Harnesses

A harness is everything an agent needs for a whole line of work. It holds:

  • AGENTS.md: what the harness is for, which file to load when, and rules that hold everywhere.
  • contexts/: context files.
  • workflows/: workflows.
  • graph/: a knowledge graph engine merged live from the recordings you choose, down to their system events.

Build one

On Harnesses, press New harness, or Build a harness on a recording, and follow the five steps:

  1. Purpose: a general name and a detailed description of what it's for.
  2. Recordings: what its graph is built from.
  3. Contexts: pick existing files. With a model, the ones that fit your description are marked Suggested. Recordings with no files yet can have them written here.
  4. Workflows: pick existing ones, and list any to write. The model proposes what's missing, and you can edit that list.
  5. Review: check the file tree, then build.

Files are copied in, so editing a harness never changes the originals, and the originals stay usable on their own. If a workflow you asked for can't be written from the recordings, the app tells you which one and builds the rest.

Edit one

Opening a harness shows an editor with three panes.

  • Left: the file tree. Use + to add a file, and Export to download.
  • Middle: tabs for open files, with Preview and Source. Save with ⌘S.
  • Right: a chat that reads every file and can edit, add, or remove them, or write a new workflow from the recordings. Each change appears as a chip you can open.

Undo reverses the last change, whether it came from the chat or from saving. Review what the chat changes, since a model can soften or misread what you asked for. Editing by chat needs a model that supports tool calls, but you can always edit in Source.

The graph engine

Open graph/engine in the tree to see the merged graph, search its entities and system events, and change which recordings it's built from.

Set up a model

Contexts, workflows, and harnesses are written by a model you choose. Open Settings › Model, open a provider, add its key, and press Use. Each provider keeps its own key and model, so you can switch at any time. Test sends one small request.

Keys can also live in a .env file in ~/.chronicle or the current directory. What you choose in Settings beats CHRONICLE_LLM, unless that's set to off, which keeps models off on this computer no matter what.

Use a local model

Anything with an OpenAI-compatible endpoint works, including Ollama and LM Studio. With Ollama running, open Local model in Settings. The endpoint defaults to http://localhost:11434/v1, and the models you've pulled appear under Model. Pick one, then press Test and Use.

ollama pull llama3.2

Chat about a recording works with any model. Workflows, harness chat, and naming context files rely on tool calls, so pick a model that supports them. Models without tool support get the tools described in the prompt instead, but small ones often fail at this: in our testing, gemma3:4b answered questions well but couldn't write a valid workflow or edit a file.

What gets sent

The provider in use receives window titles, URLs, system events, and redacted screen text. A local model keeps them on your computer. With no model, Chronicle runs fully offline and still records, builds graphs, searches, and builds plain context files.

Connect an agent

Chronicle is an MCP server. Desktop and command-line clients start it locally. In the app, Integrations shows which clients it found, in green, and connects or disconnects them.

From the terminal, install writes the server into a client's config and keeps the old file as a backup. config prints the snippet instead, and --dry-run shows what would be written. Restart the client afterwards.

How agents use it

An agent calls list_harnesses first. If one fits, it reads AGENTS.md with get_harness, loads the files it points to with read_harness_file, and looks things up with search_harness_graph. get_context adds what's on screen right now. A local server can also record on its own when an agent calls start_recording. Only one Chronicle process captures at a time.

Hosted agents and APIs

These run on someone else's servers, so they need a public HTTPS URL. chronicle serve exposes MCP at /mcp. Set a token, then put it behind a tunnel you control:

export CHRONICLE_TOKEN=$(openssl rand -hex 16)
export CHRONICLE_PUBLIC_URL=https://YOUR-TUNNEL-HOST
chronicle serve &
cloudflared tunnel --url http://127.0.0.1:3030
echo "$CHRONICLE_PUBLIC_URL/mcp/$CHRONICLE_TOKEN"

Anyone with that URL can read your Chronicle data. Stop the tunnel when you're done, and change the token if the URL leaks. Clients that support headers can use /mcp with Authorization: Bearer instead.

ChatGPT: open Settings › Connectors › Advanced, turn on Developer mode, and create a connector with that URL and no authentication. The search and fetch tools return what connectors and deep research expect.

APIs: chronicle mcp config prints a starting point for each. Provider model names and beta flags change often, so check their MCP docs too.

chronicle mcp config openai-api
chronicle mcp config anthropic-api
chronicle mcp config gemini-api
chronicle mcp config http

Fuller scripts are in examples/.

MCP server

Two transports share one set of tools: stdio with chronicle mcp, and Streamable HTTP at POST /mcp on a running server. Protocol versions 2025-06-18, 2025-03-26, and 2024-11-05 are supported. To look at it by hand:

npx @modelcontextprotocol/inspector --cli chronicle mcp --method tools/list

Resources and prompts

Resources: chronicle://context/current, chronicle://graph/summary, and chronicle://sessions. Templates: chronicle://harness/{id}, chronicle://context-file/{id}, chronicle://workflow/{id}, chronicle://context/session/{id}, and chronicle://frame/{id}.

Prompts: use_my_computer_context(task) grounds a task in Chronicle, and learn_from_recording(session_id) turns a recording into steps an agent can repeat.

REST API

curl -s http://127.0.0.1:3030/sessions
curl -s "http://127.0.0.1:3030/graph/search?q=acme"
curl -s -X POST http://127.0.0.1:3030/ask -H 'Content-Type: application/json' -d '{"question":"Acme export","session_id":1}'
curl -s -X POST http://127.0.0.1:3030/contexts -H 'Content-Type: application/json' -d '{"preset":"coding","session_id":1,"title":"Shipping exports"}'
curl -s -X POST http://127.0.0.1:3030/harnesses -H 'Content-Type: application/json' -d '{"name":"Billing","purpose":"Deliver billing exports","session_ids":[1]}'

Your data

Everything is in ~/.chronicle: db.sqlite, screenshots in media/, and capture.lock. There's no account and no telemetry. Data leaves that folder only through agents you connect and the model you choose. Delete a recording on the Recordings page, or delete the folder to remove everything.

Deleting a recording removes its frames, events, graph, and context files. Harnesses and workflows keep their own text, so delete those too if you need that gone. The full policy is in PRIVACY.md.
